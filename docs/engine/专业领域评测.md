用户实测反馈交互没问题，翻译质量是核心短板：`container orchestration engine` 被译成「集装箱管弦发动机」。
本文记录 #78 的三件事：专业领域测试集、候选模型对比、术语保护原型。**默认引擎不改**；
是否引入 LLM 由负责人和用户决定，LLM 类候选只作为对照项评测，不接入默认引擎。

结论的标注：**已测**＝本文数据在评测机上实际跑出；**推测**＝根据上游文档、模型卡或经验判断，未实测；
**待验证**＝需要别的环境（Windows 笔记本、GPU 等）才能确认。

## 怎么跑

依赖：`pip install -e "engine[eval]"`（sacrebleu、psutil）。CTranslate2 候选需要先转成 int8（见下文「候选的获取」），
LLM 候选需要 llama.cpp 的 `llama-server`。

```bash
# 快速子集（每个方向 × 领域取 2 句 + 1 段，日文方向最多 8 条，并总是包含典型译例），约 80 条
python scripts/eval_domain.py run --candidate opus-mt --quick \
  --models-dir /path/to/models --out reports/domain --threads 4

# 全量 388 条；LLM 候选要给 llama-server 路径
python scripts/eval_domain.py run --candidate hy-mt1.5-1.8b \
  --models-dir /path/to/models --out reports/domain --threads 4 \
  --llama-server /path/to/llama-server

# 多个结果合成对比报告
python scripts/eval_domain.py report reports/domain/*.json --out reports/domain/report.md
```

COMET 需要 torch，只在单独的 venv 里跑（不要装进运行环境），分数写回结果 JSON，再重新生成报告：

```bash
pip install unbabel-comet          # 在 convert 用的 venv 里
python scripts/score_comet.py reports/domain/*.json
```

LLM 候选：`LlamaServerBackend` 启动 llama-server 时固定加 `--cache-ram 0 --load-mode none`（关掉提示缓存、不用 mmap），
内存数字才能和 CTranslate2 类比较。在带 AMX 的 CPU 上，把发行包复制一份并删掉 `libggml-cpu-sapphirerapids.so`，
让 llama.cpp 选用不走 AMX 的后端（理由同下文的 MKL 问题；只复制，不要用符号链接，ggml 按可执行文件的真实路径找后端）。

`--directions en-zh,zh-en` 只跑部分方向，`--limit N` 每个方向只取前 N 条。候选清单是
`engine/eval/domain/candidates.json`，模型路径相对 `--models-dir`。

评测机上的约定：`taskset -c 0-3` 限 4 核、`--threads 4`，候选依次跑，不并行。

**评测机注意事项（已测）**：评测机是带 AMX 的 Xeon KVM 虚拟机。MKL 的 AMX int8 GEMM 在这台机器上结果不稳定：
同一句 opus-mt-en-zh int8 连跑 30 次，4 线程时 30 次输出各不相同，大多夹杂乱码；另有进程占用 CPU 时，单线程 30 次里也有 1 次乱码。
float32 或者 `MKL_ENABLE_INSTRUCTIONS=AVX512_E1`（关掉 AMX，保留 VNNI）时，30 次全部一致。
因此本文所有 CTranslate2 数据都在 `MKL_ENABLE_INSTRUCTIONS=AVX512_E1` 下测得，结果 JSON 的 `environment` 里记有取值。
推测是虚拟机没有正确保存 AMX tile 状态，与模型无关；普通笔记本 CPU 没有 AMX，不受影响（推测）。
部署时的处理见下文「部署注意事项」与「待办」。

CI（ubuntu-latest）只跑现用基线 opus-mt 在 en↔zh 上的快速子集，用来证明脚本能跑通；报告写进 job summary，
结果 JSON 作为 artifact 上传。runner 的耗时不作为性能数据。

### 观察到的问题（已测）

- **opus-tc-big**
  - en→zh 与 ja→zh 两个 tc-big 模型经常丢句末的「。」。
  - zh→en 的 tc-bible-big-zhx-en 会整段省略（zh-en-code-007、zh-en-legal-015 被截短），ja→zh 会编造内容，ja-zh-ui-001 输出为空。

- **M2M100 / NLLB**
  - 专业术语仍常直译，例如「集装箱乐队发动机」「甲状腺素」（metformin）。en→zh 的 COMET 不高于 opus-tc-big。

- **LLM**
  - HY-MT1.5 会补充原文没有的内容（en-zh-code-001），把 hosted 译成「维护」。
  - TranslateGemma 把 metformin 译成「甲磺酸二甲供体」。
  - Qwen3.5-2B 把 licensee 译成「许可方」、把「甲方」译成 the payer。

## 部署注意事项

- **带 AMX 的 CPU / 虚拟机**：
  - 已测：在评测机（Xeon，KVM）上，CTranslate2 的 int8 推理走 MKL 的 AMX 路径时会算出乱码。设 `MKL_ENABLE_INSTRUCTIONS=AVX512_E1` 后恢复正常。
  - llama.cpp 在同一台机器上默认也会用 AMX 缓冲区。本次评测改用不含 AMX 的后端，没有验证 AMX 下的结果是否正确。
  - 普通笔记本 CPU 没有 AMX，推测不受影响。
  - 在服务器 / 虚拟机上部署时，应默认设置上述环境变量，或者先用本评测连跑两次比对结果。
- **llama-server**：要加 `--cache-ram 0`，否则提示缓存最多占 8 GiB 内存。只监听 127.0.0.1。
- **tc-big 前缀**：en→zh、ja→zh 的 tc-big 是多目标模型，句首必须加 `>>cmn_Hans<<`，否则可能输出繁体或其他语种（推测）。

## 术语保护原型

**只是原型，默认关闭**：只在评测脚本里通过 `--terms protect|prompt` 开启，没有接入 `Translator` 和翻译接口，默认引擎的行为不变。

### 做法

- **protect（Marian / M2M100 等 seq2seq 模型）**：`glossary.protect()` 在原文里找术语表条目（长词优先、不重叠、英文按词边界且大小写不敏感），换成占位符 `ZXQ`、`ZXW`、`ZXJ`、`ZXK`、`ZXV`（多于 5 个时加数字）再翻译；`glossary.restore()` 把占位符写回术语在目标语言的规范写法（大小写不敏感匹配；英文句首大写；中日文去掉占位符两侧多出来的空格）。占位符丢失或重复时这条算失败，**整条回退为不保护的译文**，不会输出残缺结果。
- **prompt（llama-server 上的 LLM）**：把命中的（原文写法 → 目标写法）写进提示词。HY-MT 用它模型卡里的中文术语干预模板「参考下面的翻译：{原文} 翻译成 {译文}」，其他模型用通用英文模板。TranslateGemma 的原始模板不支持，会直接报错。
- 用法：`python scripts/eval_domain.py run --candidate opus-mt --terms protect --models-dir ... --out ...`，结果名为 `<候选>+<模式>`，统计（命中条数、占位符个数、失败、回退）写进结果的 `settings.terms`。

### 典型译例（已测，opus-mt，不保护 → 保护）

| 原文 | 不保护 | 保护 |
|---|---|---|
| Kubernetes is an open-source container orchestration engine hosted by the CNCF. | Kubernetes是一个由CNCF托管的开放源码集装箱管弦发动机。 | Kubernetes是一个由CNCF托管的开放源码容器编排引擎。 |
| The Cloud Native Computing Foundation maintains a landscape of more than a thousand projects. | 云族电子计算基金会拥有一千多个项目。 | 云原生计算基金会拥有一千多个项目。 |
| Run the migration script before you deploy the new version to the staging environment. | 在您将新版本应用到中继环境之前运行迁移脚本。 | 在将新版本安装到预发布环境之前运行迁移脚本。 |
| 容器编排平台负责调度、扩缩容和故障恢复。 | The packaging assembly platform is responsible for dispatch, scalability and malfunction recovery. | The container orchestration platform is responsible for movement control, scalability and failure recovery. |
| Kubernetesはコンテナオーケストレーションの事実上の標準になっている。（ja→en） | You can see that you've got a lot of stuff in there. | Kubernetes is the virtual standard of container orchestration. |
| …package.jsonを更新してから再実行してください。（ja→zh） | 请更新包。 Json 然后重新运行。 | 请更新 package.json 然后再重新运行。 |
| A large language model predicts the next token based on the context window.（en→ja） | 大きな言語モデルは、コンテキストメニューに基づいて次のトークンを予測します。 | 大規模言語モデルはコンテキストウィンドウに基づいて次のトークンを予測します。 |

**反例（已测）**：保护只保证术语本身，占位符周围的语法可能变差。

- 「这个接口在高并发下会出现死锁…」保护后成了 "This interface, which is expected to be deadlock high and high…"，比不保护时还差。
- 「本番環境へのデプロイは…」保护后「本番環境」对了，但没在术语表里的「デプロイ」被译成「折旧 / Depreciation」。

### 局限与待办

- 英文冠词不跟着改：占位符写回后，a / an 可能对不上（推测，偶见）。
- 占位符周围的语法可能变差（见上面的反例）；zh→en 最明显。
- opus-tc-big 本身会丢句末「。」，保护后也一样（已测）；可以在写回时补上，待办。
- 术语只做字面匹配，不处理词形变化（复数、动词变位）和同形异义；没有上下文判断（推测会有误匹配）。
- 接入产品还需要：用户术语表的格式与编辑界面、在 `Translator` 里的开关（默认关闭）、句子级回退的日志。这些不在 #78 范围内，建议另开 Issue。
- LLM 的 prompt 模式术语准确率高，但会带出 LLM 本身的语义错误（HY 会自行加内容，Qwen2B 会弄反 licensee / licensor），见「观察到的问题」。

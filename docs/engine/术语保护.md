# 术语保护（#83）

一期只做 zh↔en，不上 LLM（#78 方案 A）。本 Issue 做了三件事：

1. en→zh 模型换成 tc-big（`opus-mt-eng-zho-tc-big-2022-05-14`）。
2. zh↔en 直连时默认开启术语保护：内置 287 条术语，再加上用户术语表。
3. 所有方向补全句末标点。

结果均为 **Linux 实测**，**Windows 待测**。

## 用法

```bash
python -m suiyi_engine serve                                  # 默认开启，用户表在 <设置目录>/glossary.tsv
SUIYI_GLOSSARY=0 python -m suiyi_engine serve                 # 默认关闭
SUIYI_USER_GLOSSARY=/path/to/glossary.tsv python -m suiyi_engine serve
python -m suiyi_engine translate --src en --tgt zh "Kubernetes is an open-source container orchestration engine."
```

```powershell
$env:SUIYI_USER_GLOSSARY = "$env:APPDATA\suiyi\glossary.tsv"
python -m suiyi_engine serve
```

| 设置 | 命令行 | 环境变量 | 默认 |
|------|--------|----------|------|
| 开关 | `--glossary` / `--no-glossary` | `SUIYI_GLOSSARY`：`1/0`、`true/false`（也接受 `on/off`，不区分大小写；其他值在 stderr 告警并按开启处理） | 开启 |
| 用户术语表 | `--user-glossary <路径>` | `SUIYI_USER_GLOSSARY=<路径>` | `SUIYI_CONFIG_DIR/glossary.tsv`，否则 Windows `%APPDATA%\suiyi\glossary.tsv`，其他系统 `$XDG_CONFIG_HOME/suiyi/glossary.tsv`（默认 `~/.config/suiyi/`） |

两个设置的优先级都是：命令行 > 环境变量 > 默认值。`serve` 和 `translate` 子命令都支持。

**推荐客户端用环境变量传参，兼容老引擎**：老版引擎会忽略不认识的环境变量，但遇到不认识的命令行参数会启动失败。客户端（#84）请始终设置 `SUIYI_USER_GLOSSARY=<设置目录>\glossary.tsv`，这样两边的路径一定一致。设置页切换开关时不用重启服务，每次 `/translate` 带上 `"glossary": true/false` 即可。

HTTP 接口（`/translate` 的 `glossary` 字段、`/ocr_translate` 的同名 query 参数、`/health` 的 `glossary_*`、`POST /glossary/reload`）见 [HTTP API](HTTP-API.md)。对接约定见 [#83 的评论](https://github.com/xubin0903/suiyi/issues/83#issuecomment-5845549072)。

## 用户术语表格式

UTF-8（允许 BOM）。每行一条，列之间用 **Tab** 分隔：

```
# 以 # 开头的行是注释；空行忽略。不支持行内注释（术语本身可能含 #，如 C#）
# 源词<TAB>目标词<TAB>可选方向
container orchestration	容器编排
Kubernetes	Kubernetes
k8s	Kubernetes
预发布环境	staging environment	zh-en
API	应用程序接口
```

- **第 3 列方向**：只能是 `en-zh` 或 `zh-en`。写了方向时，第 1 列是源词，第 2 列是目标词。
- **省略方向时双向生效**：含中文字符（CJK）的那一列是中文一侧，另一列是英文一侧。
- **两列都不含中文**（如 `Kubernetes<TAB>Kubernetes`）：第 1 列是英文一侧，第 2 列是「中文里的写法」，同样双向生效。两列相同表示「保持原样，不要翻译」。
- **大小写**：英文源词匹配时不区分大小写。例外是 2 个字母以上的全大写缩写（如 `API`、`PR`），只按大小写完全一致匹配。内置表里「保持原样」类的专名（如 `Pod`、`Git`）也区分大小写。
- **复数**：英文源词的最后一个词自动匹配常见复数（`-s`、`-es`，辅音加 `y` 变 `-ies`）。不做其他词形变化。
- **边界**：英文按词边界匹配，中文按字面匹配（忽略空白）。中文原文里的拉丁词也按词边界匹配，所以 `Go` 不会匹配 `Google`。
- **合并**：同一方向、同一源词在两张表里都有时，用户条目优先。匹配时长词优先；长度相同时用户条目优先。
- **热加载**：每次翻译前检查文件的修改时间和大小（最多每秒一次），变了就重新读。`POST /glossary/reload` 可以立即重读。
- **限制**：文件最大 1 MiB，最多 5000 条。

### 出错时（术语表永远不影响翻译）

| 情况 | 处理 | 在哪里看到 |
|------|------|-----------|
| 文件不存在 | 只用内置表，不算错误 | `glossary_user_entries: 0` |
| 行级问题：缺目标词、多于 3 列、方向非法、两列都含中文、写了方向但英文一侧含中文 | 跳过这一行，其余照常 | `glossary_warnings`（保留前 20 条）、stderr |
| 文件级问题：不是 UTF-8、读不了、超过 1 MiB 或 5000 条 | 整个用户表不生效，只用内置表；改好后热加载自动恢复 | `glossary_error`、stderr |
| 内置表加载失败 | 关闭术语保护，翻译照常 | `glossary_enabled: false`、`glossary_error` |
| 翻译时占位符丢失或重复 | 这一句用不保护的译文 | 日志 `术语保护回退 en→zh builtin:deadlock:missing`，只含术语 id，**不含原文** |

## 工作方式

对每一句找出命中的术语，再把两个版本放进**同一批**解码：原句，以及把命中的术语全部换成占位符的版本。

1. 原句译文里每个术语的译法都已经对了，就用原句译文。
2. 只差空格或连字符的变体，直接改正后用原句译文（如 `dead lock` → `deadlock`，只用于英文目标、6 个字母以上）。
3. 否则用占位符版的译文，把占位符还原成术语表里的写法，并修正英文冠词 `a` / `an`（启发式）。
4. 还原失败时退回原句译文，并记一条回退日志。

只对单模型直连的 zh↔en 生效。英文中转（ja→zh）和其他语向不做术语保护。

选型实验（全量集，已测）：

| 策略 | en→zh / zh→en chrF | COMET | 段落 P95 |
|------|-------------------|-------|---------|
| 只在首遍漏掉术语时再译第二遍 | 44.3 / 62.2 | 89.54 / 86.12 | 241 ms |
| **同批推测（采用）** | 44.8 / 62.1 | 89.59 / 86.13 | 170 ms |
| 一律用占位符 | 46.1 / 61.9 | 89.10 / 86.01 | 141 ms |

一律用占位符的 chrF 最高，但 COMET 最低，语法也更差。同批推测 COMET 最好，延迟也满足要求，所以采用它。模型分数不能用来判断占位符版的好坏，因为占位符版得分反而更高（已测）。

句末标点补全对所有方向生效：原文以句末标点结尾、译文以字母 / 数字 / 汉字结尾时补上；省略号不补；中日译文里汉字后的半角 `.!?` 改成全角。tc-big 原始输出在 142 句 en→zh 中漏掉 95 句的句末标点，补全后为 0（main 的旧模型漏 18 句）。

## 前后对比（Linux 实测）

测试条件：#78 专业领域集（zh↔en 共 290 条），4 核（`taskset -c 0-3`，`--threads 4`），beam 2，int8，2026-09-26。结果文件由 `engine/eval/domain_bench.py` 生成，候选为 `suiyi-83` / `suiyi-83-noterms`。

| | en→zh chrF / COMET | zh→en chrF / COMET | 术语准确率 | 段落 P50 / P95 | 常驻内存 | 磁盘 |
|---|---|---|---|---|---|---|
| main（旧 en-zh） | 33.1 / 83.70 | 58.6 / 84.68 | 55.7% | 87 / 111 ms | 250 MiB | 160 MiB |
| tc-big + 标点，不保护 | 43.2 / 89.12 | 58.6 / 84.68 | 70.0% | 99 / 135 ms | 416 MiB | 318 MiB |
| **tc-big + 标点 + 术语保护（默认）** | **46.0 / 89.67** | **62.1 / 86.13** | **98.3%**（en→zh 99.5%，zh→en 96.7%） | 118 / **178 ms** | **434 MiB** | 318 MiB |
| 同上，`--intra-threads 2`（#87 前的服务默认） | 同上 | 同上 | 同上 | 125 / **229 ms** | 409 MiB | 318 MiB |

- 验收线：en→zh chrF ≥ 43、术语 ≥ 95%、zh→en ≥ 61.9、段落 P95 ≤ 200 ms（4 核）、只装 zh↔en 时内存 ≤ 450 MiB，都达到（内存按评测进程计，见下一节）。#87 前的服务默认 2 线程 P95 为 229 ms，超过 200 ms，所以 #87 把默认改成 `min(4, CPU 数)`。
- 术语准确率是上限：评分用的就是内置表的同一份术语。
- 保护统计：373 句中 251 句命中术语，95 句用了占位符（137 个），1 句修正了变体，5 句回退。
- 装全 6 个方向时，ja→zh 经 tc-big 中转，chrF 从 15.9 升到 27.4。其他方向不变或小幅变化，常驻内存 940 MiB。

### 服务默认线程与真实服务内存（#87，Linux 实测）

默认 `intra_threads` 改为 `min(4, os.cpu_count())`，拿不到 CPU 数时为 2。可以用 `--intra-threads` 或 `SUIYI_INTRA_THREADS` 覆盖。

测试条件：
- 2026-09-26，8 逻辑 CPU 的 Linux 虚拟机，`taskset -c 0-3` 限在 4 核；`os.cpu_count()` 仍是 8，所以默认为 4。
- `MKL_ENABLE_INSTRUCTIONS=AVX512_E1`，beam 2，int8。只装 tc-big 和 zh-en，没有用户术语表。
- 同一台机器上还有其他构建任务，负载约 1–2.5。

| 测法 | 段落 P50 / P95 | RSS |

## `/ocr_translate` 的开关（#87）

`/ocr_translate` 的请求体是 PNG 字节，参数都走 query，所以开关也是 query 参数：`?glossary=true` 或 `?glossary=false`，不传时按服务配置。老版引擎会忽略不认识的 query 参数（已在 main 3a7aebf 上实测）。

同一张截图（"Deploy the new version to the staging environment first."，`target=zh`）的实测结果：

| 请求 | 老版引擎（3a7aebf） | #87 |
|------|---------------------|-----|
| 不传 | 200 首先将新版本部署到预发布环境。 | 200 首先将新版本部署到预发布环境。 |
| `glossary=true` | 200（忽略参数）同上 | 200 同上 |
| `glossary=false` | 200（忽略参数）同上 | 200 将新版本部署到 staging 环境。 |
| `glossary=maybe` | 200（忽略参数）同上 | 422 `invalid_request` |

## 例子（已测，全量集原句）

三列分别是：main、tc-big 不保护（`suiyi-83-noterms`）、默认（`suiyi-83`）。

| 原文 | main | tc-big 不保护 | 默认 |
|------|------|--------------|------|
| Kubernetes is an open-source container orchestration engine hosted by the CNCF. | Kubernetes是一个由CNCF托管的开放源码集装箱管弦发动机。 | Kubernetes 是由 CNCF 托管的开源容器编排引擎。 | 同左 |
| The Cloud Native Computing Foundation maintains a landscape of more than a thousand projects. | 云族电子计算基金会拥有一千多个项目。 | 云原生计算基金会(Cloud Native Computing Foundation)维护着一千多个项目的景观。 | 同左 |
| Run the migration script before you deploy the new version to the staging environment. | 在您将新版本应用到中继环境之前运行迁移脚本。 | 在将新版本部署到 staging 环境之前运行迁移脚本。 | 在将新版本部署到**预发布环境**之前运行迁移脚本。 |
| Observability combines metrics, logs, and distributed tracing.（句首大写） | 可观察性结合了测量、日志和分布式跟踪。 | 可观察性结合了指标日志和分布式跟踪。 | **可观测性**结合了指标日志和分布式**追踪**。 |
| Diversification reduces the overall risk of a portfolio.（句首大写） | 多样化可减少投资组合的总体风险。 | 多样化可以降低投资组合的整体风险。 | **分散投资**可以降低投资组合的整体风险。 |
| …Recall improved by twelve points without hurting precision.（句首大写） | 回顾后提高了12点… | 记忆力提高12分… | **召回率**在不伤害**精确率**的情况下提高了12分。 |
| 容器编排平台负责调度、扩缩容和故障恢复。 | The packaging assembly platform is responsible for… | 同左 | The **container orchestration platform** is responsible for movement control, scalability and failure recovery. |
| 这个接口在高并发下会出现死锁，需要重新设计加锁顺序。 | This interface will have a dead lock when it is high and issued… | 同左 | This interface will have a **deadlock** when it is high and issued…（变体修正，没走占位符；#82 原型的占位符译文是 "…expected to be deadlock high and high…"。「high and issued」是模型本身的错误） |

前两句是换模型后就对了，不靠术语保护。

句末标点：tc-big 原始输出在 142 句 en→zh 中有 95 句漏掉句末「。」，补全后为 0。

**反例**：
- `triages`（动词第三人称）被当成 `triage` 的复数：The emergency department triages patients by the severity of their symptoms. → 不保护时是「急诊科根据患者症状的严重程度对患者进行分类。」，保护后是「急诊科分诊患者的症状严重程度。」，语法更差。
- 同一段里的 "the recall for rare categories was poor" 被译成「召回率的稀有类别较差」，术语对了但语序错了。

## 局限

- 复数规则会误匹配英文动词的第三人称（如 `triages`）。
- 占位符周围的语法问题没有完全解决（全量集 5 句回退）。以后可以试按注意力对齐直接替换。
- `a` / `an` 修正是启发式。
- **真实 `serve` 进程的常驻内存约 540 MiB，超过 450 MiB**（评测进程只有 432–436 MiB）。多出来的部分是服务本身（FastAPI、uvicorn、语种检测，不加载模型时约 133 MiB），与线程数无关。见下一节，待定。
- 常驻内存 434 MiB，接近 450 MiB 的上限。
- Windows 的延迟和内存待测。

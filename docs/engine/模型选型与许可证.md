## 2. 候选对比

Helsinki-NLP 名下核过这三类名字：`opus-mt-{src}-{tgt}`、`opus-tatoeba-{src}-{tgt}`、`opus-mt-tc-big-{src}-{tgt}`。下列仓库 API 返回 401，按不存在处理：`opus-mt-en-ja`、`opus-mt-zh-ja`、`opus-mt-ja-zh`、`opus-mt-tc-big-en-ja`、`opus-mt-tc-big-ja-en`、`opus-mt-tc-big-ja-zh`、`opus-mt-tc-big-en-zh`、`opus-mt-tc-big-zh-en`、`opus-tatoeba-ja-en`、`opus-tatoeba-zh-ja`、`opus-tatoeba-ja-zh`、`opus-tatoeba-en-zh`、`opus-tatoeba-zh-en`。

架构均来自该修订的 `config.json`（`model_type: marian`）。「base」指 d_model 512、6+6 层、8 头、FFN 2048；「big」指 d_model 1024、6+6 层、16 头、FFN 4096、词表 32001。未逐张量清点参数量。体积只计 `pytorch_model.bin`，不要把同仓库的 tf / flax / rust 文件加进去。

### 2.1 `opus-mt-en-zh` 的简体标记

模型卡写明：多目标模型，源句开头必须有 `>>id<<`。本修订 `vocab.json` 里实际存在的目标标记只有这 8 个：

| token | id | 用途 |
|-------|----|------|
| `>>cmn_Hans<<` | 5 | **简体中文，默认** |
| `>>cmn_Hant<<` | 21 | 繁体 |
| `>>cmn<<` | 361 | 未分繁简，不作为默认 |
| `>>yue<<` / `>>yue_Hans<<` / `>>yue_Hant<<` | — | 粤语 |
| `>>nan<<` / `>>wuu<<` | — | 闽南语 / 吴语 |

模型卡目标列表里还有 `gan`、`lzh`、`cjy`，这个修订的词表里没有对应的 `>>id<<`，不要照卡片去拼。

拼接方式：`>>cmn_Hans<<` 与英文之间加一个空格，例如 `>>cmn_Hans<< Hello`。manifest 的 `src_prefix_token` 不含这个空格。

zh→en 的 `metadata.json` 把 `cmn_Hant` 等列在源语言成分里，源句不加标记。繁体输入能否稳定译出，模型卡没有单独分数，见第 7 节。

## 3. 中转

### 3.1 ja→zh：经英文

```
ja --opus-mt-ja-en--> en --opus-mt-en-zh（前加 >>cmn_Hans<<）--> zh
```

没有可钉在 Hugging Face 修订号上的 Helsinki-NLP 直连模型。Tatoeba-Challenge 的 [jpn-zho README](https://github.com/Helsinki-NLP/Tatoeba-Challenge/blob/master/models/jpn-zho/README.md) 指向 CSC 上的 `opusTCv20210807_transformer-big_2022-09-15.zip`，目标含 `cmn_Hans`，且要求语言标记；公开分数是 jpn-multi BLEU 12.1，不是干净的日→中测试。社区仓库（如 `shun89/opus-mt-ja-zh`）不是 Helsinki-NLP 发布，来源未核，不进入清单。

给性能基线和评测 Issue：这一方向是两次句级解码。模型都已加载时，延迟大约是单模型的两倍，还要加上中间英文的再分词。质量会损失，损失幅度没有在同一测试集上测过，不能用两跳各自的 BLEU 相乘或相加来估算。

### 3.2 zh→ja：用直连，不中转

直连模型是上游 zip 转换的 `opus-mt-zho-jpn-tc-big-2022-07-28`（见第 10 节）。中转路径 `opus-mt-zh-en` → en→ja 不作为默认，#25 实测过：

- 随译样例上中转 chrF 18.58（第二跳用原 `opus-tatoeba-en-ja`）或 18.20（第二跳用 `opus-mt-eng-jpn-2021-02-18`），直连 31.32。
- Tatoeba-test-v2021-08-07 zho-jpn 前 500 句：中转 22.83，直连 31.16。
- 直连只解码一次。中转会把延迟大约加倍，并叠加误差。

代价是运行时要载入 transformer-big（d_model 1024），int8 目录约 212 MiB，内存高于一颗 base。

## 4. 许可证

### 4.1 清单采用 CC-BY-4.0

纳入下载的权重要按 **CC BY 4.0** 署名后再分发。原文：<https://creativecommons.org/licenses/by/4.0/legalcode>。

依据是权重发布方自己的说明，不是训练代码的 MIT：

- [OPUS-MT-train `models/README.md`](https://github.com/Helsinki-NLP/OPUS-MT-train/blob/master/models/README.md) 写明这些预训练模型使用 CC BY 4.0。
- [Opus-MT README](https://github.com/Helsinki-NLP/Opus-MT/blob/master/README.md) 同样把可下载模型和 Tatoeba Challenge 模型写成 CC-BY 4.0。
- `OPUS-MT-train` 与 `Opus-MT` 仓库根目录的 `LICENSE` 是 **MIT**，覆盖的是训练代码和服务代码，不是权重。

所核过的 HF 模型仓库 **都没有 `LICENSE` 文件**（只看了 `main` 文件树）。许可证写在模型卡 YAML，有的正文又写了一遍。

| 模型 | 模型卡 YAML | 模型卡正文 | 本清单 |
|------|-------------|------------|--------|
| `opus-mt-zh-en` | cc-by-4.0 | License: CC-BY-4.0 | CC-BY-4.0 |
| `opus-mt-tc-big-zh-ja` | cc-by-4.0 | License: CC-BY-4.0 | CC-BY-4.0 |
| `opus-mt-en-de`、`opus-mt-ru-en`、`opus-mt-tc-big-en-ko` | cc-by-4.0 | License: CC-BY-4.0 | CC-BY-4.0 |
| `opus-mt-en-zh`、`opus-mt-ja-en`、`opus-tatoeba-en-ja` 及其他 YAML 为 apache-2.0 的纳入模型 | apache-2.0 | 正文没有再写许可证 | **仍按 CC-BY-4.0 署名** |

YAML 里的 `apache-2.0` 与上游 `models/README.md` 不一致。manifest 用 `license` 记录要遵守的 SPDX（`CC-BY-4.0`），用 `hf_card_license` 保留卡片标签。按 CC BY 署名不会和 Apache-2.0 的保留声明冲突；若只信 YAML、分发时不署名，则会漏掉上游已经写明的义务。

CC BY 4.0 对随译的直接要求：

- 保留创作者：赫尔辛基大学语言技术研究组（Helsinki-NLP），并引用 Tiedemann 与 Thottingal，EAMT 2020。tc-big 模型同时引用 Tatoeba Translation Challenge（Tiedemann，WMT 2020）。
- 保留许可名称和 URI：CC BY 4.0，<https://creativecommons.org/licenses/by/4.0/>。
- 转成 CTranslate2 int8 是改编，需标明「随译改编」，不能暗示 Helsinki-NLP 认可量化结果。
- 没有 NC、没有 SA。可以随 MIT 应用按需下载分发。

[Tatoeba-Challenge 仓库根目录 `LICENSE`](https://github.com/Helsinki-NLP/Tatoeba-Challenge/blob/master/LICENSE) 的标题是 **Attribution-NonCommercial-ShareAlike 4.0**。这是该 git 仓库（数据说明、脚本、文档）的许可证文本，不是权重的。

#25 下载并核对了发布包本身：`zho-jpn/opusTCv20210807-sepvoc_transformer-big_2022-07-28.zip`、`eng-jpn/opus-2021-02-18.zip`、`eng-jpn/opus+bt-2021-04-10.zip`（即原 `opus-tatoeba-en-ja` 的来源）里都带一个 `LICENSE` 文件，内容是 **Creative Commons Attribution 4.0 International** 全文（三份逐字节相同）。权重随包附带的许可证就是 CC BY 4.0，没有 NC、没有 SA。转换脚本把这份 `LICENSE` 和 `README.md` 拷进模型目录，随模型一起分发。

所以原先「`opus-tatoeba-*` 可能受 NC-SA 约束」的风险对本清单里的日语模型不成立：en→ja 现在用的 `opus-2021-02-18` 与 zh→ja 用的 zip 都以发布包内 LICENSE 为依据。

### `en-jap` / `jap-en` 不是日语

日语的 ISO 639-1 是 `ja`，ISO 639-3 是 `jpn`。ISO 639-3 的 `jap` 是 **Jaruára**（已于 2007-07-18 弃用，并入 `jaa` Jamamadí），见 <https://iso639-3.sil.org/code/jap>。

模型卡把源或目标写成 `jap`，测试集名字是 `bible-uedin.*.jap`。抽查 OPUS 发布的 `opus-2020-01-08.test.txt`，英文对照行的系统输出含假名和汉字（圣经体日语）。这说明 OPUS 旧目录用 `jap` 标过圣经平行语料，**不能**据此把仓库登记成 `ja`。正确的英→日模型是目标语言写明 `jpn` 的 `opus-tatoeba-en-ja`。`en-jap` / `jap-en` 不进入 `models`，只出现在 manifest 的 `rejected`。

## 9. manifest 如何盖住六个方向

`tier: "mvp"` 的五条模型给出 zh→en、en→zh、zh→ja、ja→en、en→ja（zh→ja、en→ja 两条带 `weights_source`，`hf_repo` / `hf_revision` 为 `null`）。`pivots` 里 ja→zh 经由 en，且 ja→en 与 en→zh 都在 mvp 模型中。六个方向因此闭合。

```python
import json
m = json.load(open("engine/model_manifest.json"))
mvp = {(x["src"], x["tgt"]) for x in m["models"] if x["tier"] == "mvp"}
covered = set(mvp)
for p in m["pivots"]:
    assert (p["src"], p["via"]) in covered
    assert (p["via"], p["tgt"]) in covered
    covered.add((p["src"], p["tgt"]))
need = {("zh","en"),("en","zh"),("zh","ja"),("ja","zh"),("en","ja"),("ja","en")}
assert need <= covered
```

## 10. Issue #25：重选 zh→ja 与 en→ja

2026-09-25 在本机（Linux，8 逻辑 CPU，评测与基准用 `taskset -c 0-3` 限在 4 核）实测。标「实测」的是跑出来的数字；标「推测」的没有验证。

### 10.1 zh→ja 根因：HF 转换丢了源语词表

**实测结论**：`Helsinki-NLP/opus-mt-tc-big-zh-ja` 在 Hugging Face 上的权重转换有缺陷，与目标语标记无关，改生成参数也救不回来。

- 上游模型是 **分离词表**（zip 名里的 `sepvoc`）：中文源词表 `src.vocab` 与日文目标词表 `trg.vocab` 各 32000，编码器、解码器各有一张嵌入。
- HF 版只有一张 `vocab.json`（32001）和一个 `model.shared.weight [32001, 1024]`，`config.json` 为 `share_encoder_decoder_embeddings: true`，`tokenizer_config.json` 为 `separate_vocabs: false`。`vocab.json` 与上游 `trg.vocab` 重合 31999 个 token，与 `src.vocab` 只重合 9666 个。也就是说 **HF 版把日文目标词表当成了源词表**，源嵌入也随之丢失。
- 结果是中文 SentencePiece 切出的 piece 大量查不到：Tatoeba zho-jpn 前 500 句的源 piece 有 1563/3460（45.2%）变 `<unk>`。`索尼总部位于东京。` 编码成 `[<unk>, <unk>, <unk>, 。, </s>]`，于是输出 `↓↓↓↓↓`。
- 用 transformers 5.17 直接跑 HF 的三个修订：`d621a879`（当前 main）输出 `本、` / `↓↓↓`；`1499b2f1`、`0f67cf7f` 输出长串乱码。`d621a879` 本身就是 [discussions/3](https://huggingface.co/Helsinki-NLP/opus-mt-tc-big-zh-ja/discussions/3)「Update checkpoint for transformers>=4.29」合入后的版本，该 PR 自带的测试输出已经是 `挫折<unk> 星ホテル暴`。[discussions/4](https://huggingface.co/Helsinki-NLP/opus-mt-tc-big-zh-ja/discussions/4) 也报告模型卡示例无法复现。`refs/pr/1`、`refs/pr/2`（safetensors 自动转换 PR）同样实测输出乱码。HF 上没有能用的修订。
- 目标语标记：词表里没有 `>>jpn<<`、`>>jpn_Hani<<`、`>>ja<<`（上游 `src.vocab` 也没有）。在 CTranslate2 里硬加这些前缀，只会多一个 `<unk>`，输出仍是 `本、`。**负责人怀疑的「缺少目标语标记」不是根因。**
- 修复：直接下载同一次发布的上游 zip（[README](https://github.com/Helsinki-NLP/Tatoeba-Challenge/blob/master/models/zho-jpn/README.md)），用 CTranslate2 的 Marian 转换器按两张词表转换。`请给我一杯水。` → `水をください。`，`索尼总部位于东京。` → `ソニーの本社は東京にある。`。
- 预处理：上游 `preprocess.sh` 会把全角标点换成半角。实测加上后随译样例 chrF 30.55、OCR 差值 -19.21，不如不加（31.32、-5.52），因此不做。
- 同目录还有共享词表版 `opusTCv20210807_transformer-big_2022-07-29.zip`。实测随译样例 chrF 8.08，大量截断或空串，原因未深究，不采用。

### 10.4 仍存在的问题

- en→ja 仍弱（chrF 17）：短句常被截短（`I need a receipt.` → `領収書を`，`This seat is taken.` → `この席は`），专名音译不稳（Yuki → `雄基`），口语直译（`I'm down.` → `撃たれた`）。Helsinki-NLP 能再分发的英→日模型都在上表里，没有明显更好的。
- zh→ja 专名：`陈静` 未保留（丢主语），`大阪城` 译成 `大阪`；OCR 噪声 `索 尼` → `ソニ`。
- zh→ja 模型是 transformer-big，int8 目录 221.7 MB，比原 HF 转换版（215.4 MB）略大，内存对比见 [性能基线](性能基线.md)。

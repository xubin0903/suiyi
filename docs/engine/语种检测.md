# 语种检测

`suiyi_engine.langdetect.detect` 在本机离线判断语种。本机 HTTP 的 `source: "auto"` 会调用它，见 [HTTP API](HTTP-API.md)。本文登记方案、许可证和在开发环境里量到的体积与速度。检测器本身不监听端口，也不做在线检测。

## 结论

采用 **规则层 + `py3langid` 0.4.x**。

- 假名、谚文、汉字占比、西里尔字母先按文字判断，不加载统计模型。
- 以拉丁字母为主、规则无法决定时，才懒加载 `py3langid`，在 `en` / `fr` / `de` / `es` 里排序。
- 不采用 `lingua-language-detector`：Apache-2.0 可以随 MIT 客户端分发，但 wheel 约 163 MB、安装后约 292 MB，相对轻量桌面应用过重。
- 不采用 fastText `lid.176`：识别效果最好，包括纯汉字日语；模型是 **CC BY-SA 3.0**，不是与 MIT 兼容的宽松许可证，不能作为默认依赖分发。

`py3langid` 及其自带模型为 **BSD-3-Clause**。传递依赖 `numpy`（`numpy>=2`）也是 BSD / MIT / Zlib 等宽松许可证。后续 CTranslate2 的 Python 包同样依赖 numpy，检测不会再引入第二套数组库。

## 检测顺序

默认候选：`zh`, `en`, `ja`, `ko`, `fr`, `de`, `es`, `ru`。输入先做 NFKC，这样全角拉丁字母和半角片假名能落到正常码位。数字、标点和空白不计入字母。

1. 没有字母 → `und`，`method="fallback"`。
2. 含平假名或片假名字母（U+3040–U+30FF 里的字母，以及片假名语音扩展）→ `ja`。谚文更多则 → `ko`。
3. 含谚文（U+AC00–U+D7AF 及兼容字母、Jamo）→ `ko`。
4. 汉字占字母数 **严格大于** `CJK_ZH_RATIO_THRESHOLD`（`0.20`）→ `zh`。繁简都是 `zh`。
5. 西里尔字母严格多于拉丁字母和汉字 → `ru`。
6. 以拉丁字母为主：
   - `ß` → `de`；`ñ` / `¿` / `¡` → `es`；`œ` → `fr`。
   - 整段折叠后命中封闭短词表（如 `Hello`、`Merci`、`Hola`）→ 对应语种。
   - 否则调用 `py3langid`。概率 ≤ 0.30 且不超过 3 个词、候选里有 `en` 时，回退为 `en`（`method="fallback"`）。

`method` 只有 `script`（规则，含短词表和正字法）、`model`（统计模型）、`fallback`（无法判断或超短拉丁兜底）。

片假名中点 U+30FB（以及 NFKC 之后变成它的半角中点 U+FF65）**不算假名**。中文外国人名里的间隔号不能把整句判成日语。

统计模型在进程内只建一份，并且只在第一次需要拉丁统计结果时加载。`serve` 在开始监听前调用 `langdetect.warmup()` 提前加载，避免这约 0.5 s 落在第一次 `auto` 请求上（#40）；单独 `import` 或在其他场景调用 `detect` 仍是懒加载。纯中文、日文、韩文、俄文和短词表命中都不会 `import numpy`。

## 选型对比

测量环境：Linux x86_64，CPython 3.12.3，2026-09-25。工程基准是 Python 3.11；本环境没有 3.11，包要求 `>=3.10`。体积来自 `pip download` 的 wheel 和 `du` 的 site-packages。加载时间是新进程里 `time.perf_counter()` 包住「导入 + 构建检测器 + 第一次预测」。内存是 `/proc/self/status` 的 `VmRSS` 差值。热检测是预热之后、单条 ≤ 200 字的重复预测中位数。

lingua 的内存增量看起来不大，是因为大 `.so` 按页映射，RSS 只计入碰到的页。随客户端分发时要算磁盘和安装包体积，292 MB 只为语种检测不合适。

### 为什么不选 CC BY-SA 模型

fastText 的语言识别模型（含 `lid.176.bin` 与压缩的 `lid.176.ftz`）是 CC BY-SA 3.0。相同方式共享要求：分发模型或其演绎版本时保留署名，并且这些文件继续以 CC BY-SA 提供，不能改成 MIT。量化、裁剪或改写成别的格式通常算演绎。应用代码即使保持 MIT，安装包里仍然带着一份必须 SA 的模型。这不符合「依赖许可证与 MIT 兼容、可随开源客户端分发」的要求，所以不下载、不打包、不作为运行时依赖。它也不是 CC BY-NC；否决原因是相同方式共享，不是非商用条款。

若将来改用该模型，至少要单独附上 CC BY-SA 3.0 文本和 fastText / Facebook 署名，模型文件保持 SA，不能写进 MIT 许可的源码包里假装重新许可。本期不做这件事。

## 最终方案的加载与热检测

同一环境、三个新进程，调用本包的 `detect`：

| 步骤 | 结果 |
| --- | --- |
| 导入 `suiyi_engine.langdetect` | 17–25 ms。此时 `_identifier is None`，`numpy` 和 `py3langid` 都不在 `sys.modules` |
| 第一次检测中文句子 | 0.04–0.06 ms。RSS 相对导入后只增加约 0.2 MB，仍不加载模型 |
| 第一次检测英文句子（触发模型） | 三次分别为 534 / 454 / 488 ms，**中位数 488 ms**。相对中文检测之后，RSS **增加约 90 MB** |
| 热状态，200 次，≤ 200 字 | 中文中位 0.010 ms（最大 0.056 ms）；日文中位 0.007 ms（最大 0.018 ms）；中英混排中位 0.007 ms；英文句子中位 0.055 ms（最大 0.16 ms） |

热状态单次检测远小于 20 ms。488 ms 只发生在该进程第一次需要拉丁统计模型时；剪贴板里的中文和带假名的日文不付这笔成本。

复测（在已安装 `engine[dev]` 的环境里）：

```bash
python - << 'PY'

def rss():
    with open("/proc/self/status") as handle:
```

## #92 精简缓存

py3langid 加载后在服务进程里常驻约 56 MiB（numpy、97 个语种的权重、37 MiB 的 DFA 转移表），但这里只用它区分 de / en / es / fr。#92 起改成：

- 第一次需要时，在**子进程**里运行 `python -m suiyi_engine.langid_slim <路径> de,en,es,fr`，把 DFA、每个状态的输出特征和四个语种的权重导出成一个缓存文件（约 42 MB，子进程峰值约 150 MiB，一次性，约 0.5 s）。
- 之后每次启动只 `mmap` 只读打开这个文件，用纯 Python 打分。服务进程不导入 numpy；转移表只有走到的页才进内存，而且是可回收的文件页。预热从约 500 ms 降到约 7 ms。
- 缓存目录：`SUIYI_CACHE_DIR`，否则 Windows `%LOCALAPPDATA%\suiyi\cache`，其他系统 `$XDG_CACHE_HOME/suiyi`（默认 `~/.cache/suiyi`）。文件名带 py3langid 模型文件的哈希，py3langid 升级后自动重建。
- 导出、读取任何一步失败，都退回原来的 py3langid（结果相同，内存大一些），只在日志里记一行。`SUIYI_LANGID_SLIM=0` 可以强制用原来的 py3langid。

等价性（Linux 实测）：785 条拉丁文本，四语种里第一名 0 处不同，概率最大差 8.5e-6（py3langid 用 float32，这里用双精度）。单次打分 37 µs，py3langid 29 µs。经真实 `serve` 对比 308 条 zh↔en 样例（显式源语种与 `auto` 两种），译文和检测结果 0 处不同。

## 准确率与已知局限

单元测试里，中文、英文、日文（句子都带假名）各 12 条、每条至少 5 个字符，全部判对。法、德、西各 5 条走统计模型，韩文和俄文走规则，也全部判对。

另外一组中 / 日 / 英混淆样例（含繁体、中英混排、OCR 空格、半角片假名、全角英文、纯汉字日语）为 **22/22 = 100%**。纯汉字日语按下面的局限计为「判成 zh 即正确」。把法德西韩俄和纯数字符号算进去是 **37/37**。样例与断言在 `engine/tests/test_langdetect.py`。

局限：

- **纯汉字日语判成中文。** 「東京大学」「京都」「株式会社」没有假名，规则和 `py3langid` 都会给 `zh`。fastText 能判成 `ja`，但许可证不允许默认分发。出现平假名或片假名字母后判 `ja`，例如「東京大学は日本です。」
- **只要有假名字母就优先日语。** 这是「含假名 → ja」。一个平假名出现在很长的英文里也会判日语。
- **汉字占比超过 0.20 判中文。** 「这个 bug 怎么 fix」是 4 个汉字、6 个拉丁字母，占比 0.4。占比恰好等于 0.20 时不判中文，继续往下走。
- **罗马字不按日语处理。** `konnichiwa` 会走拉丁统计模型。
- **封闭词表只匹配整段短文本**，用来补统计模型在 `Hello` / `Merci` / `Hola` 上的错误，不从长句里抽词。
- **Issue #5 的 `tests/samples/zh_core_v1.jsonl` 尚未合并。** 测试在文件不存在时跳过；合并后会用 `source` / `src_lang` 再查一遍，纯汉字日语的 `ja`→`zh` 不算失败。

## API

```python
from suiyi_engine.langdetect import detect

result = detect("这个 bug 怎么 fix")
# Detection(lang="zh", confidence=0.7, method="script")
```

```python
@dataclass
class Detection:
    lang: str          # ISO 639-1，无法判断时为 "und"
    confidence: float  # 0–1
    method: str        # "script" | "model" | "fallback"

def detect(text: str, candidates: list[str] | None = None) -> Detection: ...
```

`candidates` 省略时用上面的八个语种。空列表得到 `und`。出现 `pt` 这类未支持代码会抛出 `ValueError`。脚本已经判定为日语、但候选里没有 `ja` 时返回 `und`，不会改判成中文。

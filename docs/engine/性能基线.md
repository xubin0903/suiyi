# 性能基线

复制翻译的产品要求是：本机热路径下 2 秒内出译文（见 [剪贴板与截屏可行性一页纸](../research/剪贴板与截屏可行性一页纸.md) §6）。本文件把这个要求和引擎侧的初始目标记下来，并给出在随译 HTTP 服务上的实测。

测量脚本是 `scripts/bench_service.py`。它启动 `python -m suiyi_engine serve`，从客户端计时。CI 不跑这份脚本，也不安装它的依赖。

## 怎么跑

依赖在可选组 `bench`（只有 `psutil`），不进运行时。请求用标准库 `urllib`。

### bash

```bash
pip install -e "engine[bench]"
python scripts/bench_service.py --models-dir models
```

### Windows PowerShell

```powershell
pip install -e "engine[bench]"
python scripts/bench_service.py --models-dir models
```

PowerShell 里方括号必须加引号。测前请关掉其他重负载程序。

模型需先按 [模型目录约定](模型目录约定.md) 转成 CTranslate2 int8。mvp 五个模型：

```bash
python scripts/convert_models.py --tier mvp
```

常用参数：

| 参数 | 默认 | 作用 |
|------|------|------|
| `--models-dir` | 必填 | 模型目录 |
| `--repeats` | 50 | 每个热路径样例的次数 |
| `--cold-starts` | 3 | 冷启动次数，报告取中位数 |
| `--warmup` | 3 | 计入统计前丢掉的次数 |
| `--grid-repeats` | 20 | 线程 × 束宽网格每个格子的次数 |
| `--batch-repeats` | 10 | 批量网格每个格子的次数 |
| `--no-grid` | 关闭 | 跳过网格 |
| `--out` | `reports/bench-<日期>` | 输出目录 |

脚本写出 `bench.md` 和 `bench.json`，里面有环境、三次冷启动、各样例 P50/P95/max、中转方向、三个阶段的 RSS，以及网格。`reports/` 不进 git。未达标时进程仍返回 0，对照表会标「未达标」。

带 `@pytest.mark.model` 的 `engine/tests/test_bench.py::test_bench_smoke_with_real_models` 用更少的次数走同一条路径。未设置 `SUIYI_MODELS_DIR` 时跳过，CI 不下载模型。

## 测量方法

- 子进程参数是列表，不用 shell。Linux 上新开会话，Windows 上使用 `CREATE_NEW_PROCESS_GROUP`，停止时先 `terminate` 再 `kill`。
- 冷启动：`python -m suiyi_engine serve --preload zh-en,en-zh`，从进程启动到 `GET /health` 返回 `status=ok` 且 `loaded_models` 含 `opus-mt-zh-en` 与 `opus-mt-en-zh`。做 3 次，取中位数。预加载发生在开始监听之前。
- 首译：另起一个已预加载的进程，第一次 `POST /translate`（中文短句）的客户端耗时。它不进入热路径样本。
- 热路径：每个样例先做 3 次预热，再请求 50 次。计时用 `time.perf_counter()`，包住整个 HTTP 往返。P50 是中位数；P95 是最近秩，`ceil(0.95 × n)`。
- 样例：中文短句 15 字、中文中句 50 字、英文短句 10 词、中文段落 300 字（10 句）、日文短句 18 字符（`ja→en`）。中转另测同一句日文的 `ja→zh`。
- RSS：同一个进程上三个阶段。空载（`/health` 已 ok 且尚未加载模型）、各翻译一句后的中英双向、再加载其余 mvp 模型之后。`psutil` 读取服务进程及其子进程的 RSS，采样 5 次取最大。
- 内存目标按 1024 进制：800 MB = 800 MiB，1.5 GB = 1.5 GiB。
- 段落目标表没有写分位。对照用 P95，max 一并列出。本次 max 也低于 2 秒。
- 线程网格是中文短句，`intra_threads ∈ {1,2,4}` × `beam_size ∈ {1,2,4}`，每格 20 次。批量网格是中文段落，`max_batch_size ∈ {1,8,32}`，每格 10 次。网格只用来选默认参数。

## 性能目标

参考机：4 核及以上 x64 CPU、8 GB 内存、SSD、仅 CPU。

| 指标 | 目标 |
|------|------|
| 冷启动（启动到可翻译，预加载中英双向） | ≤ 5 s |
| 中文短句（约 15 字）zh→en 热路径 | P50 ≤ 300 ms，P95 ≤ 800 ms |
| 中文中句（约 50 字）zh→en 热路径 | P95 ≤ 1.5 s |

| 服务 RSS（加载中英双向） | ≤ 800 MB |

三次冷启动：522.4 ms、505.6 ms、505.3 ms。中位数 **505.6 ms**。

预加载完成后的第一次中文短句：**53.3 ms**。样例译文：`We'll meet at 3:00 this afternoon in front of the park.`

### 热路径

| 中文短句 | zh→en | 15 字 | 1 | 42.4 ms | 43.5 ms | 48.9 ms | `opus-mt-zh-en` |
| 中文中句 | zh→en | 50 字 | 1 | 120.3 ms | 125.4 ms | 128.7 ms | `opus-mt-zh-en` |

| 中文段落 | zh→en | 300 字 | 10 | 201.0 ms | 204.5 ms | 209.1 ms | `opus-mt-zh-en` |
| 日文短句 | ja→en | 18 字符 | 1 | 64.7 ms | 66.9 ms | 72.6 ms | `opus-mt-ja-en` |
| 中转短句 | ja→zh | 18 字符 | 1 | 98.5 ms | 100.6 ms | 101.3 ms | `opus-mt-ja-en`，`opus-mt-en-zh` |

## 默认参数

网格在同一台机器上跑。中文短句，每格预热后 20 次。当时服务默认已是下面要采用的 `intra_threads=2`；格子本身都显式传了参数，不依赖默认值。

| intra_threads | beam_size | P50 | P95 | max |
|---------------|-----------|-----|-----|-----|
| 1 | 1 | 62.1 ms | 64.0 ms | 64.0 ms |
| 1 | 2 | 68.1 ms | 68.2 ms | 68.5 ms |
| 1 | 4 | 73.7 ms | 74.2 ms | 78.3 ms |
| 2 | 1 | 34.8 ms | 35.7 ms | 38.5 ms |
| 2 | 2 | 42.1 ms | 42.6 ms | 42.9 ms |
| 2 | 4 | 45.3 ms | 45.6 ms | 46.1 ms |
| 4 | 1 | 34.0 ms | 35.7 ms | 36.0 ms |
| 4 | 2 | 50.8 ms | 63.8 ms | 64.6 ms |
| 4 | 4 | 61.2 ms | 66.2 ms | 71.3 ms |

`beam_size=2` 时，2 线程的 P95（42.6 ms）是三档里最快的。4 线程的 P95 是 63.8 ms，大约慢 50%，而且 P50 到 P95 的跨度更大。1 线程的 P95 是 68.2 ms。因此默认从原来的 `min(4, CPU 数)` 改为 `min(2, CPU 数)`：短句更快，也给 WPF 客户端留出核心。1 个 CPU 的机器仍然用 1。

> **#87 更新**：#83 把 en→zh 换成 tc-big（transformer-big）并开启术语保护后，2 线程的段落 P95 升到 229 ms，超过 200 ms；4 线程是 167–181 ms（见 [术语保护](术语保护.md)）。默认因此改回 `min(4, os.cpu_count())`，拿不到 CPU 数时为 2；可以用 `--intra-threads` 或环境变量 `SUIYI_INTRA_THREADS` 覆盖。上表是 #24 时旧 base 模型的短句数据，保留作记录。

`beam_size` 保持 2。同一 intra=2 下，beam=1 的 P95 只快大约 7 ms（35.7 ms 对 42.6 ms），而 beam=2 已经远低于 300 ms。束宽影响译文质量，本基准不评质量，没有理由为这 7 ms 改默认。beam=4 更慢，也不采用。

中文段落（10 句）的批量网格，使用默认 intra=2、beam=2，每格 10 次：

| max_batch_size | P50 | P95 | max |
|----------------|-----|-----|-----|
| 1 | 796.1 ms | 809.6 ms | 809.6 ms |
| 8 | 236.5 ms | 240.6 ms | 240.6 ms |
| 32 | 198.0 ms | 198.7 ms | 198.7 ms |

32 比 8 更快，比 1 快大约 4 倍。短句只有一句，批量上限几乎不影响复制翻译。默认保持 32。

`inter_threads` 保持 1。HTTP 层对翻译加了进程内互斥，同一时刻只有一路解码，多出来的 worker 只会占内存。

热路径表就是按这组默认测的，不需要再把 intra=4 的数字当成交付结果。

## 给 M2 客户端

数字是这次 HTTP 往返，不含界面绘制。复制翻译的 2 秒是浮层预算，含界面，不含服务冷启动。

- 短句 HTTP 超时用 **1500 ms**（`max(1500, P95×3)`，向上取整到 100 ms）。本次短句 P95 是 43.5 ms，留给界面大约 1.9 秒。不要把段落和中转也卡在 1500 ms 上。
- 中文段落 HTTP 超时用 **3000 ms**，ja→zh 中转短句也用 **3000 ms**（`max(3000, P95×2)`）。本次两者的 P95 都在 210 ms 以内，3000 ms 是为更慢的 Windows 机器留的下限，不是这次测出来的耗时。
- 托盘启动时拉起服务并 `--preload zh-en,en-zh`。本次冷启动中位数 506 ms。就绪前界面显示「正在准备」，不要把这段时间算进用户按下复制之后的 2 秒。
  - #40 之后 `serve` 在监听前还会预热语种检测（约 0.4–0.5 s），冷启动相应变长：同机从进程启动到 `/health` 可用由约 0.66–0.81 s 变为约 1.07–1.17 s（Linux，3 次）。换来的是第一次 `auto` 请求不再多出约 0.5 s（往返 435–562 ms → 37–48 ms，稳态约 26 ms）。
- 预加载完成后的首译是 53.3 ms，热路径 P50 是 42.4 ms。差距不大，仍建议就绪后在后台发一条短句并丢掉结果，避免第一次复制撞上分配器和线程池的预热。Windows 上这个差距可能更大。
- 服务进程保持常驻。每次复制都新起进程，会把大约 0.5 秒的冷启动加进热路径；在更慢的磁盘上会更明显。

## 已知限制

- 只测了 CPU，没有 GPU。只测了 HTTP，没有 WPF 端到端。
- 只有这一台 Linux 虚拟机的数字。Windows x64 尚未测量；测法和记录表见 [M2 实机测试](../client/M2-实机测试.md#9-延迟记录表) §9，实测数值由负责人补填。
- CPU 型号在 `/proc/cpuinfo` 里是通用的 Xeon 字符串，不能对应到具体桌面 CPU。
- 冷启动没有在测量前清空页缓存。三次结果很接近（505–522 ms），但不能代表重启后的第一次磁盘读取。
- RSS 是服务进程及其子进程，不是整机占用，也不包括客户端。
- 网格次数少于热路径的 50 次。默认值的选择看网格，交付延迟看热路径表。
- 线程默认按中文短句选择。日文短句和中转没有单独做线程网格；它们在默认 2 线程下仍远低于目标。
- 未比较 `inter_threads`。HTTP 互斥使它保持 1。
- 不评译文质量。若以后把 `beam_size` 降到 1，需要另做样例评测。

## #92 服务进程内存

目标：真实 `serve` 进程（限 4 核）中英双向都加载后 RSS ≤ 450 MiB；只用一个方向时明显更低；热段落 P95 ≤ 200 ms；质量不变。

做了四件事：

1. **分配器**：启动时设 `MKL_DISABLE_FAST_MM=1`（MKL 不再自己缓存大块内存）；glibc 上用 `mallopt` 把 malloc arena 限为 1 个（用户自己设了 `MALLOC_ARENA_MAX` 时不动）。实测 arena 1 比 2 低约 14 MiB，延迟不变。
2. **语种检测精简缓存**：服务进程不再加载 numpy 和完整的 py3langid（约 −56 MiB 常驻，预热 500 → 7 ms），见 [语种检测](语种检测.md#92-精简缓存)。
3. **`malloc_trim`**：开始监听前、每次翻译结束安静 2 秒后、卸载模型后各调用一次，把 glibc 空闲内存还给系统。
4. **模型空闲卸载**：`--model-idle-unload`（`SUIYI_MODEL_IDLE_UNLOAD`，默认 600 秒，0 关闭）。某个翻译模型连续这么多秒没被用到就卸载，下次用到时重新加载。后台线程拿不到翻译锁时跳过这一轮，不会和正在进行的翻译抢。

Windows 上只有第 1 条的 `MKL_DISABLE_FAST_MM`、第 2 条和第 4 条生效（`mallopt` / `malloc_trim` 是 glibc 专有）。

### 实测

环境：Linux，8 个逻辑 CPU，`taskset -c 0-3`（默认 `intra_threads=4`），`MKL_ENABLE_INSTRUCTIONS=AVX512_E1`，beam 2，int8，en→zh 为 tc-big，用户术语表不存在。每次读 RSS 前等 4 秒；段落 29 条 × 3 轮。main = 71d6d18。单位 MiB。

客户端式启动（预热双向后翻译，读 RSS 不等待）：main 543 MiB，#92 418 MiB；两者加载模型时的峰值都约 549 MiB。P95 181 / 183 ms。

- Windows 的 RSS 待测；glibc 相关的两项在 Windows 上不生效。

## #96 Windows 服务进程内存

背景：负责人在 Windows 实机（f9f5c5c）上 tc-big + eng-jpn + zh-en + OCR 全部加载后，serve 的 Working Set（WS）610.7 MiB，Private Bytes 3554 MiB。目标：中英双向都用过后 WS ≤ 450 MiB，P95 不明显变差；解释并尽量降低 Private Bytes。

### 做了什么

1. **同时常驻的翻译模型上限**：`--max-loaded-models`（`SUIYI_MAX_LOADED_MODELS`，默认 2，0 不限）。要加载新模型而已满时，先卸载最久没用过的（LRU）再加载，所以加载第三个模型时峰值不会叠加三份。中英双向正好 2 个；英文中转（如 ja→zh）的两段都算最近用过，不会互相挤掉。
2. **OCR 也空闲卸载**：`--ocr-idle-unload`（`SUIYI_OCR_IDLE_UNLOAD`，默认与 `--model-idle-unload` 相同，0 不卸载）。正在识别时不卸载；卸载后 `gc.collect()`（RapidOCR 的会话之间有循环引用）再整理堆。下次 OCR 请求自动重新加载（约 1–1.5 s）。
3. **Windows 堆整理**：`memory.trim()` 在 Windows 上对每个进程堆调用 `HeapCompact`，并调用 UCRT 的 `_heapmin`，把空闲块解除提交（decommit），Private Bytes 和 WS 一起下降。调用时机与 Linux 的 `malloc_trim` 相同。**没有**用 `EmptyWorkingSet` / `SetProcessWorkingSetSize` 这类只把页面挤出 WS 的做法：那样数字变小但内存还在，下一次用到时又缺页。
4. **`OPENBLAS_NUM_THREADS=1`**（用户自己设了就不动）：numpy 自带的 OpenBLAS 按 CPU 数开线程，每个线程预留缓冲（8 核约 1.2 GiB 虚拟内存）。服务里只有 OCR 前后处理用 numpy，单线程即可；OCR 冷加载反而更快（本机 1782 → 829 ms）。

### 为什么 Private Bytes 远大于 WS

- **MKL 的 int8 权重预打包（packed GEMM）**。在 Intel CPU 上 CTranslate2 默认用 MKL，加载时把每个线性层的权重按 MKL 的格式重新打包。MKL 给打包缓冲申请的大小远大于权重本身，但只写其中一部分：本机 tc-big 这块映射 1080 MiB，常驻只有 169 MiB。没写过的部分在 Windows 上仍然计入提交（Private Bytes），但不占物理内存，也不在 WS 里。
- **OpenBLAS 线程缓冲**：见上面第 4 条，也是只提交、基本不碰。
- **AMD CPU 不受影响**。CTranslate2 在 AMD 上默认用 oneDNN，不打包，Private ≈ WS。GitHub 的 Windows runner 就是 AMD EPYC 7763，所以要在 runner 上复现负责人的现象，得设 `CT2_USE_MKL=1` 强制走 MKL（见下表）。
- 打包可以关：`CT2_PACKED_GEMM=0`，或设 `CT2_USE_MKL=0` 改用 oneDNN。两者都让 Private ≈ WS，但本机段落 P95 分别慢约 30% 和 20%（下表），所以**默认不关**，只作为内存优先时的开关。Private Bytes 是提交量，只在提交总量接近上限（物理内存 + 页面文件）时才有影响。

本机（Linux，Intel，4 核，段落 29 条 × 3 轮）中英双向用过后的对比，单位 MiB / ms：

| 指令集 | 后端 | RSS | VmData（≈ 提交） | P50 | P95 |
|---|---|---|---|---|---|
| AVX-512 | MKL + 预打包（默认） | 408 | 2375 | 126 | 195 |
| AVX-512 | MKL，`CT2_PACKED_GEMM=0` | 406 | 506 | 158 | 257 |
| AVX-512 | oneDNN（`CT2_USE_MKL=0`） | 414 | 518 | 149 | 234 |
| AVX2 | MKL + 预打包（默认） | 407 | 2225 | 156 | 263 |
| AVX2 | MKL，`CT2_PACKED_GEMM=0` | 406 | 509 | 209 | 346 |
| AVX2 | oneDNN（`CT2_USE_MKL=0`） | 410 | 498 | 196 | 334 |

AVX2 一行是用 `CT2_FORCE_CPU_ISA=AVX2`、`MKL_ENABLE_INSTRUCTIONS=AVX2`、`ONEDNN_MAX_CPU_ISA=AVX2` 模拟的。在 Intel 上打包几乎不增加常驻内存，只增加提交量，而且快 20–30%。

## #104 OCR 独立子进程

OCR 从 serve 主进程挪进按需启动的子进程 `ocr-worker`（机制见 [HTTP API · OCR 子进程](HTTP-API.md#ocr-子进程104)）：
- 主进程不再导入 onnxruntime / OpenCV / numpy。
- 子进程空闲 `--ocr-idle-unload` 秒后退出，这些内存全部还给系统。
- 子进程处理完请求、安静 2 秒后会 `gc.collect()` 并整理堆（与主进程 `ModelJanitor` 相同）。不整理的话，Linux 上用过一次 OCR 后子进程常驻会从约 160 MiB 涨到约 330 MiB。

内存有两种口径：
- **主进程**：serve 进程自己。
- **合计**：主进程加 OCR 子进程；子进程退出后等于主进程。

单位都是 MiB。

### 结论

- **只算主进程**：带 OCR 的桌面端默认状态从约 540 降到约 410（Linux RSS），Windows runner 上 WS 515 → 417，满足 #96 遗留的「带 OCR 也 ≤ 450」。
- **合计**：OCR 子进程在内存里时比进程内多约 30 MiB（Linux 570 vs 542，Windows WS 544 vs 516），这是第二个 Python 解释器加上 onnxruntime / OpenCV 的重复开销。子进程空闲退出后，合计就等于主进程，比进程内卸载后的 main 少约 95 MiB（Linux 410 vs 507）。
- 翻译和热 OCR 的延迟不变。OCR 冷启动慢 0.4–1.2 s，只发生在空闲退出后的第一次框选。

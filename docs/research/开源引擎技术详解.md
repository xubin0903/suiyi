# 随译 · 开源翻译引擎深度技术介绍

> **调研日**：2026-09-20（Asia/Shanghai）  
> **产品约束**：不用商业云翻译作主路径；开源、免费、轻快；剪贴板 + 截屏 OCR；「随意翻译」为主，长文需一定上下文；核心引擎一套 + 各端薄客户端。  
> **证据纪律**：【已知】可核验来源；【推测】合理推断未直接证实；【待验证】未查到 / 无法实测 / 二手冲突。查不到写「未查到」。禁止编造参数。

## 1. TL;DR（开源路线下最值得认真评估的几类）

在**禁止商业云作主路径**的前提下，随译的开源候选可压成三类：

| 优先级【推测】 | 技术栈 | 一句话 |
|----------------|--------|--------|
| **P0 认真评估** | **Bergamot / Firefox Translations 风格端侧量化 NMT**（或同源 Marian 学生模型 + 本地推理） | 体积小、CPU 可跑、隐私好、适合剪贴板「秒出」；中文已进 Firefox 官方语种列表【已知】 |
| **P0 认真评估** | **OPUS-MT / Argos 双语句对 + CTranslate2** | 许可证友好（模型多为 CC BY；Argos 代码 MIT）、中英日韩有现成包、CPU-only 可行、与「本地 HTTP 服务」契合 |
| **P1 长文补强** | **本地小 LLM（Qwen/Gemma/Llama 等，经 Ollama 或自建）** | 上下文窗口优势明显，适合偶发长文连贯；但冷启动、内存、延迟明显高于专用 NMT【已知架构差异 + 推测体验】 |
| **P2 备选** | **MADLAD-400（Apache-2.0）** | 多语种单模型、许可证友好；3B 起，比 bilingual Opus 重，适合服务端或较强本机【已知】 |
| **谨慎 / 默认不入主路径** | **NLLB 官方权重（CC BY-NC）**、**LibreTranslate 整仓 AGPL 嵌入闭源分发**、**SeamlessM4T / Tower 的 NC 权重** | 许可或体量与「免费开源客户端分发」冲突【已知】 |

**核心结论（草案，不拍板）**【推测】：短句/OCR 碎片走轻量 NMT（Bergamot 或 Opus/Argos+CT2）；偶发长文/需指代连贯切本地小 LLM；统一本地引擎进程，各端薄客户端。

## 2. 概念地图

### 2.1 翻译范式

| 范式 | 是什么 | 典型代表 | 长文上下文 |
|------|--------|----------|------------|
| **规则 / 浅层转移** | 词典 + 形态 + 转移规则 | Apertium | 无文档级语义；规则可跨句但弱 |
| **统计 MT（SMT）** | 短语表 + 语言模型 | Moses（历史） | 句级为主 |
| **神经 NMT（encoder-decoder Transformer）** | 专用翻译模型，句/段输入 | Opus-MT、Argos、NLLB、Bergamot 学生模型 | 多数**句级独立**；文档级需专门训练或工程拼接 |
| **端侧量化 NMT** | 蒸馏 + int8/低精度 + WASM/原生 | Bergamot / Firefox Translations | 同 NMT，偏网页句块 |
| **LLM 生成式翻译** | 通用因果 LM + 指令/模板 | Qwen、Gemma、Tower、ALMA | **上下文窗口天然可用**（数千～数十万 token） |

### 2.2 与随译的集成形态

```
┌─────────────┐     ┌──────────────────────────┐
│ 各端薄客户端 │────▶│ 本地核心引擎（一套）      │
│ Win/安卓/…  │◀────│  • 短路径：轻量 NMT       │
└─────────────┘     │  • 长路径：可选本地 LLM   │
                    │  • OCR 前处理（另议）     │
                    └──────────────────────────┘
```

| 形态 | 说明 | 适合随译？ |
|------|------|------------|
| **嵌入客户端库** | 如 Bergamot WASM/原生、CTranslate2 绑定 | 延迟最低；打包与多端 ABI 成本高【推测】 |
| **本地 HTTP/IPC 服务** | LibreTranslate 风格、自写 thin server + CT2 | **与「核心一套 + 薄客户端」最契合**【推测】 |
| **自建远程服务器** | 用户或项目自托管 GPU/CPU | 违背「轻快默认离线」除非高级选项 |

## 3. 逐引擎详解

### 3.1 LibreTranslate（及背后 Argos）

#### A. 技术是什么
- **架构**：神经 NMT；引擎实际由 **Argos Translate** 驱动（OpenNMT 训练链路 + **CTranslate2** 推理）。【已知】https://github.com/LibreTranslate/LibreTranslate  
- **形态**：自托管 **HTTP API + Web UI**（Docker 友好）。  
- **与随译**：适合作为「本地/自建 HTTP 服务」参考实现；**不宜把 AGPL 服务端代码直接嵌进要闭源分发的二进制而不做合规设计**【已知 AGPL 风险】。

#### B. 语种
- 取决于所装 Argos 包；官方 Argos 列表含 Chinese / Japanese / Korean 等与 en 的双向包。【已知】https://github.com/argosopentech/argos-translate  
- **一对一包 + 英语枢轴（pivot）**：无直达对时经 en 中转，质量会掉。【已知】

#### C. 体量与部署
- 服务端镜像 + 按需模型；单包量级见 Argos 节（中英约 70 MB 级）。  
- CPU-only 可行。【已知社区用法】  
- 【能耗/算力】笔记本 CPU 可跑短句；多语种全装磁盘与内存压力大【推测】。

#### D. 速度
- 短句本地通常亚秒～秒级（硬件相关）；冷启动需加载已装包。【待验证：随译目标机实测】  
- 「秒出」：模型已热时可接近；首次安装/切换语种有等待。【推测】

#### E. 准确度
- 社区口碑：可用、弱于商业 NMT。【社区；盲测待验证】  
- 句级；SBD 分句后翻译，**非文档级**。【已知 Argos 文档：约 ~150 token 输入上限】https://argos-translate.readthedocs.io/  
- OCR 噪声 / 口语碎片：【待验证】

#### F. 许可证
- **代码：AGPL-3.0**【已知】https://github.com/LibreTranslate/LibreTranslate  
- 对开源客户端：若修改并以网络服务形式提供，需遵守 AGPL 源码义务；分发策略需法务复核。【已知法律特征】

#### G. 优缺点与适合度【推测评分】
- 优点：开箱 API、生态大、离线自托管成熟。  
- 缺点：AGPL；质量中等；枢轴损耗。  
- **适合随译场景：5/10**（作参考或严格 AGPL 合规自托管可以；作默认可分发核心引擎偏风险）。

### 3.2 Argos Translate（独立库）

#### A. 技术是什么
- Python 库 / CLI / GUI；**CTranslate2 + SentencePiece**；可选 Stanza/SpaCy 做句边界。【已知】https://github.com/argosopentech/argos-translate  
- 集成：嵌入 Python 服务，或被 LibreTranslate 包裹。

#### B. 语种
- 官方 README：Arabic、Chinese、Japanese、Korean、… 等 30+ 语种及更多。【已知】  
- 索引含 `zh↔en`、`zt↔en`、`ja↔en`、`ko↔en` 等。【已知】https://raw.githubusercontent.com/argosopentech/argospm-index/main/index.json  
- 一对一 `.argosmodel`；无直达则 pivot。

#### C. 体量与部署（调研日实测 Content-Length）
| 包 | 约大小【已知·HTTP Content-Length·2026-09-20】 |
|----|-----------------------------------------------|
| `translate-zh_en-1_9.argosmodel` | **74,481,402 B ≈ 71.0 MB** |
| `translate-en_zh-1_9.argosmodel` | **70,743,021 B ≈ 67.5 MB** |
| `translate-ja_en-1_1.argosmodel` | **117,155,716 B ≈ 111.7 MB** |
| `translate-ko_en-1_1.argosmodel` | **118,852,077 B ≈ 113.3 MB** |

文档称「平均约 100MB/对」。【已知】  
CPU 推理可行；内存：单模型数百 MB 量级为常见量级【推测，待实测】。

#### D. 速度
- CT2 加速下短句可接近交互；段落受分句与序列长度影响。【推测】  
- 冷启动：首次加载包。【待验证】

#### E. 准确度
- 中英：社区「够用」；非顶级。【社区 + 待盲测】  
- **句级**；长文连贯靠上游拼接，无原生文档上下文。【已知】  
- OCR 噪声：【待验证】

#### F. 许可证
- **代码：MIT 或 CC0 双许可**【已知】  
- **模型包许可**：索引 JSON **未逐包声明许可证** → **【待验证】分发前必须逐包核对**（历史讨论中存在「模型许可不清」风险）。

#### G. 优缺点【推测】
- 优点：体积友好、中英日韩现成、MIT 代码、易做本地服务。  
- 缺点：质量中等；模型许可需清点；句级。  
- **适合随译：7.5/10**（短路径强候选，许可清点是 blocker 之一）。

### 3.3 OPUS-MT / Helsinki-NLP + CTranslate2

#### A. 技术是什么
- **OPUS-MT**：Helsinki-NLP 用 **Marian** 在 OPUS 语料上训练的大量双语/多语方向模型。【已知】https://github.com/Helsinki-NLP/Opus-MT  
- **CTranslate2**：OpenNMT 出品的快速 Transformer 推理引擎（量化 int8/fp16 等），可转换 Marian/OPUS-MT。【已知】https://opennmt.net/CTranslate2/guides/opus_mt.html  
- 注：Faster-Whisper 同属 CT2 生态但是 **ASR**，与文本翻译无关，本文不展开。

#### B. 语种
- 宣称 **1000+** 预训练模型、**150+** 语种、**1200+** 方向量级（EasyNMT 等二手汇总）。【已知汇总】  
- 中英：Hugging Face `Helsinki-NLP/opus-mt-zh-en`、`opus-mt-en-zh` 等现成。【已知】  
- **一对一（每方向一模型）**为主；扩展新方向需找现成或自训。

#### C. 体量与部署
- 典型单方向约 **~300 MB**（EasyNMT 表）。【已知二手表】https://pypi.org/project/optimumEasyNMT/  
- `opus-mt-zh-en` 的 `pytorch_model.bin` 约 **312 MB**【已知 HF 文件信息】  
- CT2 量化后磁盘与内存显著下降；公开 benchmark 示例（en-fi Opus）：CT2 int8 CPU 约 **696 tok/s、峰值内存约 516 MB**（对比 Transformers ~147 tok/s、~2.3 GB）。【已知·特定模型/硬件】https://huggingface.co/gaudi/opus-mt-en-fi-ctranslate2  
- CPU-only：**可行且常见**。【已知】

#### D. 速度
- 见上 tok/s 量级（硬件相关）；短句热路径可「秒出」级。【推测 + 公开 bench】  
- 冷启动：加载 CT2 模型（百 ms～数秒，视盘与大小）【待验证】

#### E. 准确度
- 学术友好；质量随语料资源高低变化；中英「中等可用」【社区/学术；待盲测】  
- **句级**；文档级需自行：滑动窗口、前文拼接、术语表约束等工程手段。【推测常规做法】

#### F. 许可证
- 仓库：**MIT**【已知】  
- 预训练模型：多为 **CC BY 4.0**【已知】→ 开源客户端分发相对友好（保留署名）。

#### G. 优缺点【推测】
- 优点：许可清晰、方向全、CT2 快、CPU 友好。  
- 缺点：每方向一模型占磁盘；质量不如大多语/LLM；需自建服务封装。  
- **适合随译：8.5/10**（短路径最稳妥候选之一）。

### 3.4 Marian NMT

#### A. 技术是什么
- 纯 **C++** 高效 NMT 工具包（训练+推理）；Transformer 等。【已知】https://github.com/marian-nmt/marian  
- **框架层**：OPUS-MT、Bergamot 学生模型训练/推理链路都与 Marian 渊源极深。  
- 与随译：一般不「直接当产品引擎」，而是「训练/兼容层」；推理更常转 CT2 或 Bergamot WASM。

#### B. 语种
- 取决于所加载模型（如 OPUS-MT）。

#### C–E
- 体量/速度/质量均**模型决定**；原生 Marian 推理也很快，但 CT2 在部分公开对比中更省内存。【已知对比见上】

#### F. 许可证
- **MIT**【已知社区与项目常见声明；以仓库 LICENSE 为准】

#### G. 【推测】适合随译作**基础设施了解：6/10**；不作终端用户默认运行时首选。

### 3.5 Bergamot / Firefox Translations（端侧量化）

#### A. 技术是什么
- **Bergamot Translator**：面向浏览器/端侧的 MT；Marian 学生模型 + 量化；可编 **WASM**。【已知】https://github.com/browsermt/bergamot-translator  
- **Firefox Translations**：Firefox 内置网页翻译；本地推理、不上传页面内容（Mozilla 产品表述）。【已知】https://www.firefox.com/en-US/features/translate/  
- Mozilla 训练管线与模型托管：https://github.com/mozilla/translations  
- 与随译：**嵌入库（WASM/原生）或抽模型 + 自有推理**；高度匹配「轻快 + 隐私」。

#### B. 语种
- Firefox 官方列表示例含：**Chinese (Simplified/Traditional)、Japanese、Korean、English** 等 50+。【已知·2026-09-20 页面】同上 URL  
- 多为 **xx↔en 方向模型**；非 en 对非 en 常经 **英语枢轴**【已知 Bergamot/Firefox 设计】。

#### C. 体量与部署
- WASM 引擎制品压缩约 **1.2 MB** 量级（Firefox CI fetch 记录 bergamot-translator.wasm.zst size 1211955）。【已知】  
- 历史扩展文档：每语言对压缩约 **~40 MB** 量级。【已知·2023 文】https://andrenatal.com/2023/05/firefox-translations-how-we-did-it/  
- 当前各语种 tiny/base 精确 MB：**以 Mozilla Models 看板为准**【待验证逐模型】https://mozilla.github.io/translations/firefox-models/  
- CPU-only：**设计目标即为端侧 CPU**【已知】  
- 【能耗】笔记本 CPU 网页翻译可交互；核显无强依赖；独显非必须【推测】。

#### D. 速度
- 面向实时网页块翻译；短句适合「秒出」体验。【产品设计意图·已知】  
- 精确句/秒：未查到统一公开数 → **【未查到 / 待实测】**

#### E. 准确度
- Mozilla 自述：达 Google Translate COMET 一定比例后才进 Release（约 5% 内等准则，以官方文档为准）。【已知政策表述】  
- 中英质量：【待验证盲测】  
- 句/块级；非文档级 LLM 式上下文。OCR 噪声：【待验证】

#### F. 许可证
- 引擎与 Firefox 训练相关代码/模型分发：**MPL-2.0**【已知】https://github.com/browsermt/bergamot-translator 、https://github.com/mozilla/translations  
- MPL 对文件级开源义务相对 AGPL 对「整服务传染」更温和，但仍需合规打包。【已知特征】

#### G. 【推测】
- 优点：端侧、隐私、中文已支持、体积友好、体验对齐剪贴板。  
- 缺点：枢轴；模型矩阵与随译打包链路需自建；质量随方向不均。  
- **适合随译：9/10**（短路径首选候选）。

### 3.6 NLLB（Meta）及蒸馏/量化变体

#### A. 技术是什么
- **No Language Left Behind**：多语种 encoder-decoder；Fairseq 训练；HF Transformers 可用。【已知】  
- 变体：MoE 54.5B；Dense 3.3B / 1.3B；**Distilled 1.3B / 600M**【已知】https://github.com/facebookresearch/fairseq/blob/nllb/README.md  
- 推理：Transformers / 社区 **CTranslate2 int8** 转换（如 HF 上 `*-ct2-int8` 仓库）。

#### B. 语种
- **200** 语种；单模型多向；含中英日韩相关 Flores 代码。【已知】  
- 扩展：官方模型已覆盖广；自训成本高。

#### C. 体量与部署
- Distilled **600M**：社区 CT2 int8 `model.bin` 约 **~600 MB** 量级。【已知社区卡】  
- 1.3B / 3.3B 显著更大；完整精度多 GB。  
- CPU：600M int8 **可行但偏沉**（内存常见需数 GB 级【推测/社区】）；入门独显更舒适。【推测】

#### D. 速度
- 慢于小 bilingual Opus；短句可交互，段落更吃算力。【推测】  
- 不适合作为「默认秒出」唯一引擎，除非强量化 + 预热。【推测】

#### E. 准确度
- 论文 FLORES-200 等显示多语种强，尤其低资源。【已知论文方向】  
- 仍以句/短段为主；非 LLM 长窗。OCR：【待验证】

#### F. 许可证 — **关键 blocker**
- **权重：CC BY-NC 4.0**【已知】HF `facebook/nllb-200-distilled-600M` 等  
- **代码（fairseq 等）偏 MIT**，但 **NC 权重禁止商业用途** → 随译若以「可商用开源产品」或应用商店分发，**默认不能依赖官方 NLLB 权重**【已知】

#### G. 【推测】**适合随译作默认引擎：2/10**（研究/非商业插件或可；主路径否）。**许可是硬 blocker。**

### 3.7 M2M100 / SeamlessM4T（文本相关部分）

#### M2M100
- **A**：Many-to-many 多语 NMT；418M / 1.2B 等。【已知】https://huggingface.co/facebook/m2m100_418M  
- **B**：约 **100** 语种、直连多向；含 zh/ja/ko。【已知】  
- **C**：EasyNMT 表：418M 约 **1.8 GB**；1.2B 约 **5.0 GB**【已知二手表】  
- **F**：HF 卡 **418M 标注 MIT**【已知】——相对 NLLB 友好。  
- **G**【推测】：许可尚可，但体积与速度不如 Opus/Bergamot 贴合「轻快」→ **5.5/10**。

#### SeamlessM4T（文本简述）
- 主打 **语音+文本** 多模态；文本 I/O 约 96 语种；Large ~2.3B。【已知】https://github.com/facebookresearch/seamless_communication  
- **权重 CC BY-NC 4.0**【已知】→ 与 NLLB 类似，**不宜作随译主路径**。  
- 若随译不做语音翻译，**性价比低**；此处从简。

### 3.8 Softcatalà / Apertium（规则与混合）

#### Apertium
- **A**：经典 **规则/浅层转移 RBMT**；模块化管道。【已知】https://github.com/apertium/apertium  
- **B**：欧洲/区域语种强；**中文不在主流稳定语言对之列**【已知概况】→ 对随译中英主场景几乎无关。  
- **C–D**：极轻、CPU 秒级；无神经大模型负载。  
- **E**：近缘语种可很好；远缘/中英不适用。  
- **F**：引擎与数据常见 **GPL**【已知项目传统】  
- **G**【推测】：随译主路径 **1/10**；仅作「规则引擎对照」或小语种实验。

#### Softcatalà
- 加泰罗尼亚语社区；**NMT（OpenNMT-tf 等）+ 仍提供 Apertium 兼容 API**【已知】https://github.com/Softcatala/nmt-softcatala  
- 模型以 **Catalan↔欧洲语** 为主；模型文件常见数十 MB 级示例。【已知仓库/社区】  
- 对随译中英：**低相关**；作「社区自托管 NMT 服务」参考即可。【推测适合度 2/10】

### 3.10 本地 LLM 开源翻译路径（独立节）

#### A. 技术是什么
- 用 **Llama / Qwen / Gemma** 等开源因果 LM，经指令模板做翻译；运行时常见 **Ollama**（本机便捷）、**vLLM**（服务端吞吐）、llama.cpp / 各绑定。  
- 架构类型：**LLM 生成式翻译**（非专用 encoder-decoder NMT）。

#### B. 语种
- 取决于基座多语能力；Qwen 系列中英日韩实务中常用【社区】；精确覆盖【待验证各模型卡】。

#### C. 体量与部署
| 配置【量级·已知常识 + 推测】 | 磁盘 | 内存/显存 |
|------------------------------|------|-----------|
| 1–3B 量化（Q4 等） | ~1–2 GB | 笔记本 CPU/核显边缘可跑 |
| 7–9B 量化 | ~4–6 GB | 16GB 内存或入门独显更稳 |
| 14B+ | 更大 | 倾向独显/服务器 |

相对 NMT：同「可用翻译」下 LLM **重一个数量级以上** 很常见。【推测】

#### D. 速度
- 短句：小模型量化后可亚秒～数秒；大模型明显慢于 CT2 Opus。【推测】  
- 冷启动：加载 GGUF/权重可达数秒～数十秒。【待验证】  
- **默认剪贴板秒出：不如轻量 NMT**【推测】

#### E. 准确度与长文上下文（关键）
- **优势**：上下文窗口（常见 4k–128k+，视模型）可把**前文、术语、文体**一并喂入，指代与术语更稳。【已知 LLM 能力】  
- 专用翻译微调（ALMA、TowerInstruct 等）在论文基准上可很强，但许可/体量另论。  
- 通用 LLM：偶发胡译、漏译、格式漂移；需约束解码/后处理。【社区】  
- OCR 噪声：LLM 有时更能「猜」残缺句，也可能幻觉。【待验证】

#### F. 许可证
- **逐模型**：Llama 系 Community License；Qwen/Gemma 各有协议；**必须逐卡核对**。  
- 翻译专用：  
  - **TowerInstruct**：HF 标 **CC BY-NC-4.0 + Llama 2 Community**【已知】→ NC 限制  
  - **ALMA**：代码 MIT；权重衍生自 Llama 2 → **仍受 Llama 2 条款约束**【已知衍生关系】；HF 卡表述以具体仓库为准  

#### G. 对比专用 NMT【推测】

| 维度 | 轻量 NMT | 本地小 LLM |
|------|----------|------------|
| 短句延迟 | 优 | 中～差 |
| 长文连贯 | 弱（句级） | **强（窗内）** |
| 安装包/内存 | 优 | 差 |
| 术语/礼貌/语域 | 弱 | 较强（可 prompt） |
| 确定性 | 较高 | 较低 |

**适合随译**：**长文/高级模式 8/10**；**默认短路径 4/10**。

## 5. 架构建议草案（不拍板）【推测】

面向「**随意短译 + 偶发长文要上下文**」：

```
剪贴板/OCR 文本
        │
        ▼
  长度/用户开关判断
   ┌────┴────┐
   │短句/碎片│              │长文/需连贯│
   ▼                      ▼
 轻量 NMT 热路径          本地小 LLM 冷路径
 (Bergamot 或             (Qwen/Gemma 等 1–7B 量化
  Opus/Argos+CT2)          Ollama 或自建)
   │                      │
   └──────────┬───────────┘
              ▼
        统一结果回写剪贴板/UI
```

**配套工程（建议）**：
1. **统一本地引擎进程**（HTTP/IPC），各端只做唤起与展示。  
2. NMT 侧：预加载常用中英（及日韩）方向；SBD 分句；可选**术语表**与**滑动窗口前文**（伪文档级）。  
3. LLM 侧：默认关闭或「长文模式」；限制 max tokens；固定翻译 system prompt。  
4. **不做**默认依赖 NLLB/Seamless/Tower 官方 NC 权重。  
5. LibreTranslate：可作开发期对照，产品分发避开 AGPL 传染或整体 AGPL 开源随译。
